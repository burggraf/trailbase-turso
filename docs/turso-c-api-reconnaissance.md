# Route A C-API reconnaissance

## Verdict

**A SQLite-named C API really exists at the pinned Turso revision; a complete SQLite C substitution does not.** `upstream/turso/bindings/c` is a Rust implementation of exported `sqlite3_*` entry points backed by Turso core (with a small C varargs shim), and it produces `lib`, `cdylib`, and `staticlib` targets. It is explicitly partial, has absent entry points that TrailBase calls, and exports some functions whose bodies panic via `todo!()`. Route A is suitable for a small compatibility/link spike, but **not a drop-in substitution for pinned TrailBase unchanged** based on the source inventory.

Pins checked with `git rev-parse HEAD`: Turso `e6c79b43cabde627ab9eb4eaa20c2d3e6d384d7c`; TrailBase `12d3343d7d78c8e4dd65af264a3244f472de450d`. The plan calls for Route A first and Route C after broad API/SQL incompatibility (`trailbase-turso-prototype-plan.md:106-132`). No project or upstream files were changed; no build, link, install, or runtime test was run.

## Key Code and compatibility findings

### The C API target and supported linking

- The package is named `turso_sqlite3`; Cargo declares `crate-type = ["lib", "cdylib", "staticlib"]`. Features include empty `capi = []` and `sqlite3 = []` declarations (`bindings/c/Cargo.toml:3-23`). The workspace includes this package (`Cargo.toml:3-25`).
- There is a documented standalone C linking recipe: build the crate, then link C code using `-L.../target/debug -lturso_sqlite3`; the README's C test makefile does this (`bindings/c/README.md:32-64`). `build.rs` also compiles `src/varargs.c` with `cc` (`bindings/c/build.rs:1-15`). This is a C-callable library, not just a Rust API or an SQLite C wrapper around system SQLite.
- **No TrailBase/rusqlite substitution configuration is present in the inspected manifests.** TrailBase enables `rusqlite`'s `bundled` feature plus `cache`, `column_decltype`, `functions`, `backup`, and `preupdate_hook` (`upstream/trailbase/Cargo.toml:84-89`). Simply adding/linking the separate Turso library does not demonstrate that rusqlite's bundled SQLite was replaced. A patched `libsqlite3-sys`/rusqlite linkage or equivalent wrapper integration would need to be part of the spike; no such integration was found.
- The C package feature `sqlite3` is not evidence of substitution: the build script uses it for static SQLite compatibility tests on MSVC and requires static vcpkg SQLite (`bindings/c/build.rs:34-61`).

### Symbols: real support, absent APIs, and panic stubs

- The C API exports real `sqlite3_open`, `sqlite3_open_v2`, prepare/step/bind/result and other entry points; for example `sqlite3_open` is `#[no_mangle]` and reaches Turso core (`bindings/c/src/lib.rs:506-530`), and prepare/step are implemented (`1048-1146`, `1200-1243`). C callers can therefore use a meaningful SQLite-like subset.
- The stub macro expands to `todo!("... is not implemented")`, not an SQLite error return (`bindings/c/src/lib.rs:71-75`). Examples exported but stubbed include `sqlite3_trace_v2` (`860-870`), `sqlite3_serialize`/`sqlite3_deserialize` (`1629-1649`), all `sqlite3_backup_*` functions (`1977-2008`), and `sqlite3_create_window_function` (`3346-3359`). A call is a panic path, not a usable implementation; C-ABI panic is fatal in practice. This was source-checked, not executed.
- Two TrailBase calls have no corresponding `sqlite3_*` implementation/export in `bindings/c/src/lib.rs`: `sqlite3_auto_extension` (TrailBase CLI calls it at `trail.rs:52-55`) and `sqlite3_preupdate_hook` (production `install_hook` calls rusqlite's preupdate hook at `records/subscribe/hook.rs:39-53`). COMPAT also lists auto-extension and preupdate hook as unsupported (`COMPAT.md:695-709`, `832-840`). A substitution-only link is therefore expected to fail when those references are routed exclusively to this library; this exact link failure has not been run.
- Backup is a slightly different blocker: TrailBase implements backup and restore through `rusqlite::backup::Backup` (`sqlite/connection.rs:278-328`, `sqlite/util.rs:147-189`). Turso has the named `sqlite3_backup_*` exports, but they are panic stubs (`bindings/c/src/lib.rs:1977-2008`), so symbol presence is not functional compatibility.
- There is no SQLite C virtual-table module API (`sqlite3_create_module`, `sqlite3_declare_vtab`, etc.) in the C implementation; COMPAT marks that family unsupported (`COMPAT.md:813-830`). The TrailBase CLI initializes `sqlite-vec` as a C auto-extension (`trail.rs:52-55, 802-815`), so this is not an abstract API gap: that startup extension path is part of TrailBase's executable. Turso's own vector/FTS features are not evidence that the SQLite `sqlite-vec` extension ABI or its `vec0` module is compatible.
- Important source-vs-documentation discrepancy: COMPAT labels `sqlite3_create_function_v2` a stub/unsupported (`COMPAT.md:711-742`), but the pinned source implements a **scalar-only** bridge (`bindings/c/src/lib.rs:3249-3344`). It ignores the function flags/encoding and registers with `false, 0` (`3323-3335`); aggregate/window functions are not supplied. TrailBase registers many scalar functions (`extension/src/lib.rs:82-98`) and marks them deterministic/innocuous (e.g. `extension/password.rs:98-105`), so basic scalar registration exists but flag and schema-execution semantics remain unverified. `sqlite3_complete`, `sqlite3_sql`, `sqlite3_expanded_sql`, and `sqlite3_create_collation_v2` also have source implementations despite COMPAT's table saying otherwise in places (`lib.rs:3174-3209, 3410-3420, 2010-2043`). Prefer source for symbol existence and test actual behavior; don't use the COMPAT table as an exact export manifest.

### TrailBase's real SQL/hooks/extensions surface

- The default connection setup executes `journal_size_limit`, `trusted_schema`, `case_sensitive_like`, and `optimize`, besides busy timeout, WAL, synchronous, foreign keys, temp store, and cache size (`extension/src/lib.rs:28-48, 53-79`). Turso COMPAT marks `journal_size_limit`, `trusted_schema`, and `optimize` unsupported, and `case_sensitive_like` deprecated/not needed (`COMPAT.md:214-284`). The Rust calls propagate a rusqlite error if one is returned. **Whether each unsupported PRAGMA errors, silently no-ops, or has partial semantics is not established here**; therefore startup success and intended security/LIKE behavior are unknown until tested.
- Migrations use `PRAGMA foreign_key_check` (`refinery/src/drivers/rusqlite.rs:50-64`) and disable/re-enable foreign keys; the compatibility table says `foreign_key_check` is unsupported but `foreign_keys` is supported (`COMPAT.md:236-241`). Schema alteration explicitly executes `defer_foreign_keys` and toggles `legacy_alter_table` (`core/admin/table/alter_table.rs:108-153`), both marked unsupported (`COMPAT.md:236,255`). Treat migration/alter-table behavior as a required semantic test, not a minor unused API gap.
- TrailBase needs ordinary triggers in its auth migration (`core/migrations/main/V1__initial.sql:45-84`) and generated file-deletion triggers (`core/schema_metadata.rs:210-227`). COMPAT says CREATE TRIGGER is supported (`COMPAT.md:105-118`), but the manual says “No triggers,” “No views,” and “No savepoints” (`docs/manual.md:95-108`). The docs conflict; there is no TrailBase-on-Turso pass to resolve it.
- TrailBase registers user scalar SQL functions, including `jsonschema` in a CHECK constraint (`extension/jsonschema.rs:185-225`; migration at `core/migrations/main/V1__initial.sql:75-78`). Turso's scalar bridge is promising for the simple callback shape, but its discarded flags and custom-function-in-schema behavior need a direct test. Turso's built-in `json_each` is listed supported (`COMPAT.md:530-536`); this does not replace TrailBase's custom `jsonschema` function.
- TrailBase's realtime/record subscription path installs a preupdate hook and forwards insert/update/delete row IDs and values (`core/records/subscribe/hook.rs:39-109`, `state.rs:234-279`). This is production behavior, not only a unit test. Turso's C API lacks that hook. COMPAT's Turso-specific `capture_data_changes_conn` is a possible native alternative to investigate, **not established as equivalent** to this hook or as available through the Rust API used here.
- TrailBase's public wrapper is concretely rusqlite-oriented: `Connection::new` takes a builder returning `rusqlite::Connection` (`sqlite/connection.rs:28-46`), and backup/open paths call rusqlite directly (`275-328`). That makes a native backend broader than changing a single library name.

### Toolchain and docs

- Turso pins Rust `1.88` (`upstream/turso/rust-toolchain.toml:1-3`); TrailBase's core package declares `rust-version = "1.95"` and edition 2024 (`upstream/trailbase/crates/core/Cargo.toml:1-7`). A combined experiment must reconcile on at least TrailBase's declared minimum; no toolchain compatibility build was run. Turso's C binding also needs a C compiler through the `cc` build dependency and the C varargs shim.
- COMPAT explicitly says SQLite file format is fully supported but SQL and C API are partial (`COMPAT.md:66-80`). Its detailed API table confirms broad gaps in hooks, loadable extensions, virtual-table module calls, and backup (`695-840`); its FTS section says SQLite FTS3/4/5 is unsupported (`1150-1162`). The manual's C API section calls it a subset and only documents basic open/prepare/step/column calls (`manual.md:495-548`). The manual's compatibility paragraph is older/in conflict with the detailed COMPAT table, so guarantees for triggers/views/savepoints are **unknown without tests**.

## Route C implications if A is rejected

Route C is the plan's appropriate next estimate if the missing hooks, extension-loading/virtual-table API, and backup stubs must remain. Turso's native `turso` crate exposes distinct `Database`, `Connection`, `Statement`, and row APIs; database build is async and its statement stepping can yield for I/O (`bindings/rust/src/lib.rs:327-379, 413-442`; `connection.rs:123-151`). TrailBase currently wraps rusqlite in its own executor and exposes rusqlite-typed builders/closures (`upstream/trailbase/crates/sqlite/src/sqlite/connection.rs:28-46`). Expect adapters or rewrites for connection/pool/executor lifecycle, statements/rows/values/errors, transactions, custom SQL functions, migrations, and backup/provider lifecycle—not a mechanical dependency swap.

Specifically, evaluate a native CDC replacement for record subscriptions, Turso-native vector functionality versus TrailBase's `sqlite-vec` virtual table, and a provider-owned backup/restore path. None of those equivalences is proven from this inspection. The future cloud provider boundary in the plan remains useful, but native Route C does not by itself prove cloud durability, snapshot, hook, or compatibility guarantees.

## Residual risks / unknown guarantees

- No build, linker experiment, C fixture, Rust test, SQL test, or runtime check was performed (per instruction); every predicted linker or panic result is unobserved.
- `COMPAT.md` and the manual contradict each other on triggers/views/savepoints, and some C API table entries contradict current source. Test exact pinned behavior rather than infer it from status labels alone.
- Unsupported PRAGMA return behavior, TrailBase startup under Turso, trigger behavior, custom UDF flags/schema use, preupdate/CDC parity, and `sqlite-vec` compatibility are unknown.
- A Route A link may require modifying the SQLite wrapper or `libsqlite3-sys` build integration; the standalone C library's documented link recipe is not evidence that bundled rusqlite can be redirected to it.
- Combined Rust toolchain/build compatibility and native Route C parity are unvalidated.
