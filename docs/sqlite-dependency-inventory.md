# TrailBase SQLite Dependency Inventory — Phase 1

**Pinned source:** `upstream/trailbase` at `12d3343d7d78c8e4dd65af264a3244f472de450d` (verified with `git rev-parse HEAD`; `git status --short` was empty). All citations below are paths relative to that checkout. This is a read-only source inventory for Route A planning, not a compatibility result: no build, tests, linker inspection, dependency installation, or engine comparison was run.

**Severity key:** **High** = required by normal SQLite runtime or correctness-sensitive; **Medium** = required by particular runtime/configuration or schema workflow; **Low** = test/example/benchmark or separately packaged path; **Unverified** = source scan did not establish a runtime requirement or compatibility result. “Required” means observed in TrailBase source, not that Turso has been tested against it.

## Executive result

TrailBase's primary native database path is not a thin SQL-only interface: it is a worker-thread pool of `rusqlite::Connection`s, directly using prepared-statement caching, declared column types, user-defined scalar functions, SQLite transactions, a pre-update hook for realtime, and the online backup API. It also has a process-level SQLite auto-extension path for `sqlite-vec`. Core startup uses SQLite-specific PRAGMAs, schemas and introspection; built-in SQLite migrations depend on custom UDFs, `STRICT`, triggers, foreign keys, `UNIXEPOCH`, and `RETURNING` in callers.

No in-scope `FTS5` use was located. This is **not** proof FTS5 is absent from the bundled binary or unnecessary for arbitrary tenant SQL. The concrete vector-search extension is `sqlite-vec` (including `vec_f32` / `vec_distance_L2` in an example), not FTS. Native PostgreSQL is a separate, feature-gated backend, but TrailBase still creates SQLite logs/session databases in `AppState`; PostgreSQL does not remove the SQLite runtime dependency.

No Route A blocker or compatibility success can be asserted without building/linking and running tests against the pinned Turso C API. The source does expose a concrete, testable API/SQL contract below.

## Connection creation, ownership and concurrency

### Runtime construction flow

- `trailbase-sqlite::Connection::with_opts` accepts a rusqlite connection builder (`crates/sqlite/src/sqlite/connection.rs:29-60`); `Connection::open_in_memory` passes `rusqlite::Connection::open_in_memory` as that builder (`connection.rs:52-59`). `generic::Connection` has the analogous SQLite builder (`crates/sqlite/src/generic.rs:72-90`).
- The SQLite executor invokes the builder for a writer and for each reader, applies `query_only`/busy timeout options, forces a single connection for in-memory DBs, and assigns connections to worker threads (`crates/sqlite/src/sqlite/executor.rs:57-146`). Core chooses 2–4 workers for file-backed main DBs by default (`crates/core/src/connection.rs:519-538`).
- `Connection` is cloneable over an `Arc` executor. The executor serializes writer access and assigns each reader connection to one worker; it documents an unsafe `Sync` invariant that the same rusqlite handle must never be accessed concurrently because of its statement cache (`crates/sqlite/src/sqlite/executor.rs:10-22,117-146,324-391`). Close sends worker termination and closes each owned rusqlite handle (`executor.rs:296-321`); clones can observe shared close (`crates/sqlite/src/sqlite/connection.rs:342-347`). A Route A replacement must preserve single-handle ownership/serialization, not merely expose a Send/Sync-looking pointer.
- Native main/attached DB workers are built with `trailbase_extension::connect_sqlite`, then get the 256-entry statement cache, optional LiteGIS registration, and configured WASM scalar functions (`crates/core/src/connection.rs:478-503`). The builder runs for each executor connection, so connection-local UDF registration is repeated per handle.
- `connect_sqlite` opens file handles with `READ_WRITE | CREATE | NO_MUTEX`, or opens in memory; registers TrailBase functions; applies PRAGMAs; and runs `optimize` (`crates/extension/src/lib.rs:53-79`). Core has a second raw open helper for logs/session/backup DBs at `connection.rs:635-655`, then registers functions separately for logs/session (`connection.rs:582-632`). `AppState` constructs logs and session SQLite DBs before selecting the main SQLite/Postgres backend (`crates/core/src/app_state.rs:90-115`).
- Persistent names are `main.db`, `session.db`, and `logs.db` under `data/`; configured DBs are `{name}.db` and backups/migrations have their own directories (`crates/core/src/data_dir.rs:18-54`). SQLite attachments are capped to 124 beyond main (125 including main); attached DBs are migrated as main on a temporary connection before attach (`crates/core/src/connection.rs:470-575`).
- `Options::read_only` is implemented by setting `PRAGMA query_only = true` on an otherwise built connection; the open flags above remain read-write/create (`crates/sqlite/src/sqlite/executor.rs:24-37`, `crates/core/src/connection.rs:635-646`). This is not an OS-level read-only open.

## SQLite-facing API, C symbols, functions and extensions

### rusqlite-facing runtime contract

- Open/path/options: `Connection::open_with_flags`, `open_in_memory`, `path`, `busy_timeout`, `pragma_update`, `set_prepared_statement_cache_capacity`, plus rusqlite close/drop. Core opens `NO_MUTEX`; its wrapper controls which worker owns each connection (`crates/extension/src/lib.rs:53-79`, `crates/core/src/connection.rs:635-655`, `crates/sqlite/src/sqlite/executor.rs:57-146,296-321`).
- Statements/results: `prepare_cached`, `rusqlite::Batch`, `Rows`, `Statement::columns()` and `Column::decl_type()` (`crates/sqlite/src/sqlite/sync.rs:58-117`, `sqlite/batch.rs:9-65`, `sqlite/util.rs:29-82,133-143`). Query results are eagerly materialized (`sqlite/src/traits.rs:10-22`, `sqlite/src/rows.rs:41-53`).
- Sync/async abstraction: `SyncConnection` exposes query-row(s), execute and execute-batch; `SyncTransaction` adds commit/rollback/expanded SQL (`crates/sqlite/src/traits.rs:6-32`). - Batch semantics are custom: `Connection::execute_batch` iterates `rusqlite::Batch` using `raw_query`; a separate `trailbase_sqlite::execute_batch` returns rows from the final statement, used by the admin SQL endpoint (`crates/sqlite/src/sqlite/sync.rs:99-118`, `sqlite/batch.rs:9-65`, `crates/core/src/admin/query.rs:108-132`). - Errors: Core inspects rusqlite extended SQLite error codes when translating record errors (`crates/core/src/records/error.rs:27-70`); a duplicate-primary-key test asserts extended code `1555` (`crates/core/src/auth/error.rs:100-150`). - Parameter styles seen in native SQL include SQLite `$1` and named parameters (e.g. `auth/api/login_anonymous.rs:65-75`, `records/write_queries.rs:126-132`). A Pg-specific SQL rewriter/binder is separate (`crates/sqlite/src/pg/util.rs:25-70`).

## Pre-update hook and realtime data path

**High / correctness-sensitive.** Core `install_hook` takes a write lock, installs rusqlite `preupdate_hook`, maps INSERT/UPDATE/DELETE to `RecordAction`, copies row id/cells, and sends events through a bounded channel of 16,384 (`crates/core/src/records/subscribe/hook.rs:27-112`). The wrapper's write lock dereferences the first connection (writer connection) only (`crates/sqlite/src/sqlite/lock.rs:13-56`); Core writes are serialized to that writer (`sqlite/src/sqlite/executor.rs:213-250,324-391`). Subscription state installs the hook and spawns a broker (`crates/core/src/records/subscribe/state.rs:220-278`); events are converted to JSON and filtered/delivered (`state.rs:465-505`). SSE/WebSocket subscription routes are only mounted for SQLite (`crates/core/src/records/mod.rs:45-65`); no Postgres equivalent hook is present.

**Silent correctness risks to test:**

1. Hook events are enqueued at pre-update time, with no commit-hook/rollback reconciliation in the inspected path. A write in a transaction which later rolls back can therefore be exposed as an event unless another layer prevents delivery. This is a hypothesis from the code path, not a tested failure: compare hook callbacks (`hook.rs:48-100`), transaction lifecycle (`crates/sqlite/src/sqlite/connection.rs:131-147`) and async broker (`state.rs:243-278`).
2. The callback increments `cnt` before `try_send`; a full queue drops an event. The broker treats a sequence gap as a reason to clear subscriptions and stop (`hook.rs:76-96`, `state.rs:245-264`). This is explicit lossy/backpressure behavior, not a lossless commit log.
3. `extract_record_values` maps failed per-column conversions to `Value::Null` (`crates/sqlite/src/sqlite/util.rs:100-129`), which can silently make a realtime payload differ from the stored row. Unknown actions/rowids are also skipped (`hook.rs:53-74`).
4. UPDATE rowid extraction uses the *new* rowid (`sqlite/util.rs:87-98`), while record subscriptions are keyed by the looked-up current `_rowid_` (`core/records/subscribe/state.rs:286-305`). An explicit rowid change could make record-level matching miss the old subscription key; no such test was run.

The `preupdate_hook` feature and its old/new value / row-id / column-count semantics are non-optional for current SQLite realtime behavior. No `update_hook` use was located.

## Transactions, migrations and schema SQL

### Transaction behavior

- SQLite `Connection::transaction` starts rusqlite `conn.transaction()` on the writer and passes a `rusqlite::Transaction` to user code (`crates/sqlite/src/sqlite/connection.rs:131-147`). The closure does not auto-commit; call sites explicitly commit or rely on rusqlite transaction drop/rollback. Generic mode similarly branches to SQLite or Postgres transactions (`crates/sqlite/src/generic.rs:210-232`).
- `OwnedTx` holds a write lock with a self-referential rusqlite transaction; it is `unsafe impl Send` and commits/rolls back using SQL `COMMIT`/`ROLLBACK` (`crates/sqlite/src/sqlite/transaction.rs:105-177`). WASM can retain that transaction lock (`crates/wasm-runtime-host/src/sqlite.rs:1-45` and `crates/sqlite/src/sqlite/transaction.rs:111-177`). This is a particularly concrete lifetime/ownership port boundary.
- Refinery has both a rusqlite sync driver and TrailBase async driver. Each executes migrations transactionally, temporarily turns foreign keys off outside the transaction, checks `PRAGMA foreign_key_check`, commits, then restores the FK pragma (`crates/refinery/src/drivers/rusqlite.rs:31-89`, `drivers/trailbase.rs:23-101`). The migration table is SQLite `STRICT` in both (`rusqlite.rs:100-110`, `trailbase.rs:112-130`).
- Core applies embedded base + main migrations, then user migrations from `migrations/main` recursively and legacy top-level migration files (`crates/core/src/migrations.rs:47-92,219-239`). Logs/session have distinct embedded migration sets (`migrations.rs:105-132,313-336`). File names are parsed/sorted before application (`migrations.rs:219-239,263-306`).

### Backup/checkpoint/lifecycle

- SQLite backup uses rusqlite's `backup::Backup::new_with_names`, copies 128 pages per step, handles `More`, retries `Locked`/`Busy` up to 100 times, and errors on other results (`crates/sqlite/src/sqlite/util.rs:147-191`). `Connection::backup`, `backup_to_dir`, and `restore` open raw destination/source rusqlite handles (`sqlite/connection.rs:278-329`; generic counterpart `generic.rs:437-510`).
- Core backup explicitly rejects non-SQLite main backends, enumerates main/logs/session plus configured attached DBs, and separately backs up/restores each file (`crates/core/src/backup.rs:24-81,91-138`). `DataDir` and backup paths are filesystem-owned (`crates/core/src/data_dir.rs:18-54`). This conflicts with the future provider boundary unless those path/backup responsibilities are moved below it.
- **No explicit `wal_checkpoint`, `sqlite3_wal_checkpoint*`, `VACUUM INTO`, or savepoint call was located in the scoped source search.** WAL mode is enabled; a scheduled SQLite maintenance task calls `PRAGMA optimize` (`crates/extension/src/lib.rs:28-50`, `crates/core/src/scheduler.rs:426-440`). Absence in this scan is not a statement about implicit engine checkpoints.

**Silent backup risks:** `backup_all` logs and skips a DB when `connect_backup_db` fails, without adding that failure to the error vector (`backup.rs:60-68`); it can then return `Ok` when the remaining copies succeed (`backup.rs:78-84`). Restore similarly skips a DB whose target connection failed (`backup.rs:126-138`) and can return `Ok` if no recorded copy error exists (`backup.rs:144-149`). Separate per-file snapshots are not one atomic snapshot across main/session/logs/attached DBs. These behaviors should be tested before any durability claim.

## Native SQLite versus PostgreSQL

- `core` feature `pg` enables `trailbase-sqlite/generic` (`crates/core/Cargo.toml:27-34`); workspace `trailbase` requests `wasm` and `pg` (`Cargo.toml:95`). `ConnectionManager` selects `init_db_pg` when a PG URI is provided, otherwise `init_db_sqlite` (`crates/core/src/connection.rs:120-158`). PG opens `postgres::Client` via `pg_with_opts`, applies PG-specific migrations and explicitly does not support read-only or multi-DB attachment in the cited code (`connection.rs:427-459`; `crates/sqlite/src/generic.rs:97-114,185-232`).
- Generic wrapper dispatch is explicit on `Executor::Sqlite` vs `Executor::Pg` for queries, execute and transactions (`crates/sqlite/src/generic.rs:14-30,185-232,237-400`). PG uses its own thread executor and query parameter serializer (`crates/sqlite/src/pg/executor.rs:33-110`, `crates/sqlite/src/pg/util.rs:25-70`) rather than SQLite handles.
- Main SQLite schema discovery reads `sqlite_schema` and parses SQL; PG uses `trailbase-pg-schema` (`crates/core/src/schema_metadata.rs:232-314`). Admin SQL query editor currently rejects PG (`crates/core/src/admin/query.rs:54-62`); admin schema listing has a PG-specific catalog path and does not provide CREATE TABLE SQL (`crates/core/src/admin/table/list_tables.rs:47-100`). Record SQL varies by backend (`crates/core/src/records/record_api.rs:767-890`, `records/list_records.rs:235-265`); SQLite relies on `_rowid_`, PG on `ctid` (`crates/core/src/util.rs:10-23`).
- Realtime subscription routes are mounted only for SQLite (`crates/core/src/records/mod.rs:45-65`), and Core backup rejects PG (`crates/core/src/backup.rs:24-32`). Nevertheless SQLite remains required in a PG-enabled app for logs/session DBs: `AppState::init` opens both before `ConnectionManager::new` selects the main backend (`crates/core/src/app_state.rs:90-115`); those factories are SQLite (`crates/core/src/connection.rs:582-632`).
